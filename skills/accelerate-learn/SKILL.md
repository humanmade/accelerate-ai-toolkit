# Accelerate -- Update your site's learning journal

You read the site's completed A/B test results, classify each experiment into a canonical suggestion pattern, and update the site's learning journal so every other skill can tailor future recommendations to what has worked here.

**This skill is read-only on WordPress.** You never create, modify, or stop experiments. You write two local files only.

## Step 1 -- Fetch site context

Call `accelerate/get-site-context` with `blocks: "none"`. You need `site.name`, `site.theme` (when present), and `site.url` to derive the site key.

### Site key derivation rule

This is the canonical rule. No other skill implements its own version. The key identifies *one site's design* — the thing we are optimizing — so it combines the site's name, its active theme, and a stable hash of its URL.

**Key format:** `<site-name-slug>-<theme-slug>-<url-hash>`

Build each segment:

1. **`site-name-slug`** — slugify `site.name` from `get-site-context`: lowercase, replace any run of non-alphanumeric characters with a single hyphen, strip leading/trailing hyphens. Example: `"Example Co."` -> `example-co`.
2. **`theme-slug`** — slugify `site.theme` from `get-site-context` the same way, **if it is present**. If `get-site-context` does not return a theme (older plugin versions don't expose it), **omit this segment entirely** and fall back to `<site-name-slug>-<url-hash>`. Never error or block on a missing theme — degrade gracefully.
3. **`url-hash`** — a short, stable hash of the **full** `site.url` (including protocol, host, and port). Take the first 8 hex characters of its md5:

   ```bash
   printf '%s' "<site.url>" | md5sum | cut -c1-8   # or: md5 -q -s "<site.url>" | cut -c1-8 on macOS
   ```

Examples:
- name `"Example Co."`, theme `"twentytwentyfour"`, url `https://www.example.com:8080` -> `example-co-twentytwentyfour-3f9a2c11`
- same site on a plugin that doesn't expose the theme -> `example-co-3f9a2c11`

**Why the theme is in the key:** two sites can share a display name yet be different things we must not mix — a staging copy and its production original commonly share a name but run different themes, and the *design* (the palette, typography, and section vocabulary we optimize) is tied to the theme, not the name. Including the theme keeps their journals and brand context separate. The URL hash separates same-named sites that share a host (e.g. several local sites on `localhost`), which a bare hostname cannot.

**The bare hostname is banned as the key.** Deriving the key from `site.url`'s host alone collides every site that shares a host (all local sites resolve to `localhost`) and silently cross-contaminates their learning history. Always use the name + theme + hash format above.

**No migration of old flat files.** Earlier toolkit versions stored flat `journal-<hostname>.*` and `brand-<hostname>.md` files keyed on the hostname. Those are **abandoned, not migrated** — on first run under the new key a fresh per-site journal starts. The old flat files can be deleted manually; the toolkit never reads them again.

### Per-site store layout

Each site's files live in a per-site subdirectory keyed by the rule above:

- `~/.config/accelerate-ai-toolkit/sites/<key>/journal.json` — machine-readable journal (source of truth)
- `~/.config/accelerate-ai-toolkit/sites/<key>/journal.md` — human-readable summary, regenerated from the JSON
- `~/.config/accelerate-ai-toolkit/sites/<key>/brand.md` — brand context (design tokens; generated by `accelerate-test`)
- `~/.config/accelerate-ai-toolkit/sites/<key>/brandpack.json` — bounded structure and palette cache

The shared `~/.config/accelerate-ai-toolkit/env` credentials file stays where it is — it is not per-site.

## Refresh budget and receipt

A normal refresh is deliberately bounded. Its maximum is **14 reads** (one site context read, five history-list pages, and eight detailed results), **1 MiB of returned data**, and **45 seconds elapsed**. Stop before the next read would exceed any limit. Keep a local receipt for this run only: read count, received bytes, elapsed time, list pages examined, detailed results read, cache/reuse state, and whether a limit stopped the work. Never send this receipt anywhere.

The history listing is a reconciliation, not a cursor. The producer supports `page` and `per_page`; it does **not** support an update cursor or `updated_since`. Start at page 1 with `per_page: 100`, then read at most five pages. The producer returns newest-created experiments first. If `pages` is greater than five, record and say that this pass covered the newest 500 completed experiments, not all history. Do not claim complete coverage or silently truncate.

## Step 2 -- Reconcile the bounded completed history

Call `accelerate/list-experiments` with `status: "completed"`, `type: "all"`, `per_page: 100`, and `page: 1`. Read up to page 5 only while the refresh budget remains. For each listed item, make an identity fingerprint from:

`experiment_id`, `block_id`, `test_id`, `type`, `status`, `title`, `goal`, `started_at`, `ended_at`, `has_winner`, `winner_variant_index`, `annotations`, `updated_at`, and `result_revision`.

`annotations` are part of the fingerprint; an annotation correction is a changed record. On current producers, `result_revision` is a fingerprint of stored results and the variant snapshot, so a corrected historical result is also a changed record. `updated_at` is supporting metadata, not a cursor.

Read the journal before detailed results. Compute each listing hash with the bundled `scripts/learning.py` function `listing_fingerprint(listed_item)`, using a local Python import; do not invent a serialization or ask the model to calculate a hash. Compare that value specifically with `journal["experiments"][str(experiment_id)]["listing_fingerprint"]`, not the record's overall `fingerprint` (which also includes detailed results and classification). Match each listed identity this way:

- An unchanged fingerprint needs **no** historical detailed-result call.
- A new or changed fingerprint needs one `accelerate/get-experiment-results` call with `experiment_id`.
- Process at most eight new/changed records per refresh, ordered by newest `ended_at`, then `experiment_id`. State how many eligible records remain for a later bounded refresh.

This means a repeated, unchanged refresh makes zero historical detailed-result calls. One newly listed completed experiment makes one detailed-result call unless an explicit budget limit stopped the pass.

### Older producer coverage

If `result_revision` is absent, retain the listing fingerprint for winner, end-state, and annotation changes, but set `listing_coverage.result_correction_coverage` to `"partial"`. Say that the installed site cannot detect a correction limited to historical result metrics until it supplies a result revision. Do **not** invent an update cursor and do not periodically re-read unchanged historical details just to hide this gap.

## Step 3 -- Read the existing journal

Read `~/.config/accelerate-ai-toolkit/sites/<key>/journal.json` if it exists.

- **File missing:** Start with an empty journal structure. (This is expected on a site's first run under the new key — old flat `journal-<hostname>.*` files are not read or migrated.)
- **Invalid JSON / parse error:** Do not overwrite. Stop and tell the user: *"Your learning journal appears to be corrupted. You can delete it and I'll rebuild from scratch, or restore it from a backup."* Do not proceed.
- **`schema_version` is newer than `4`:** Stop and tell the user: *"Your learning journal was created by a newer version of the toolkit. Please update the toolkit to read it."* Do not proceed.
- **`schema_version` is older than `4`:** Do not merge into it. Offer the explicit bounded rebuild path below. It creates the version 4 journal only from the pages and detailed results actually collected, and labels the result as partial if the full history did not fit the stated limits.
- **Valid:** Parse and continue.

## Step 4 -- Classify each experiment

For each experiment:

### 4a. Determine the pattern

Read `annotations['toolkit:pattern']` from the experiment's annotations object.

- If present and matches a pattern_id in the taxonomy below: use that pattern.
- If present but not in the taxonomy: classify as `other` and record the annotation value in the pattern's notes.
- If `annotations` is missing or doesn't contain `toolkit:pattern`: classify as `other`.

No keyword fallback. No hypothesis text parsing. Classification is a pure dictionary lookup.

### 4b. Distinguish proof from selection

The completed state, winner index, and applied content do **not** reveal whether a person selected a variant or a statistically valid result was observed. Never treat `has_winner`, a winner index, or producer-applied content as proof by itself. A detailed result with `selection_provenance: manual` is durable evidence of a manual choice.

Use one explicit evidence value for every record:

| Evidence observed in this session | Journal outcome | Counts toward learning? |
|---|---|---|
| A gate-valid result was observed and recorded during this supervised session | `proven_result` → win, loss, or inconclusive | Yes |
| The detailed result returns `selection_provenance: manual`, or the user selected a variant during this session | `manual_selection` | No; keep it visible separately |
| Historical result with no recorded decision evidence | `unknown_selection` | No; keep it visible separately |

Only `proven_result` may classify a non-control winner as a win or a control winner as a loss. A historical listing normally starts as `unknown_selection`; do not backfill proof from the winner index. The application action is a separate fact from the decision provenance.

### 4c. Compute lift for proven wins

For a `proven_result` win, lift is `((winner_conversion_rate - control_conversion_rate) / control_conversion_rate) * 100`. The control is variant index 0. If the control conversion rate is zero, missing, or invalid, store `null`, never infinity or a fabricated percentage.

## Step 5 -- Merge idempotently and atomically

Build the bounded refresh payload with the site identity, the explicit `listing_coverage` object, and each new/changed record's listing, detailed result, pattern, short composition summary, and evidence value. Run the bundled helper from the toolkit root:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/learning.py" merge \
  --journal "$HOME/.config/accelerate-ai-toolkit/sites/<key>/journal.json" \
  --summary "$HOME/.config/accelerate-ai-toolkit/sites/<key>/journal.md" \
  < <bounded-refresh-payload>
```

The helper takes an exclusive local lock, verifies both the site key and full URL, identifies entries by `experiment_id`, and replaces an existing entry only when its fingerprint changed. It recomputes the pattern totals from those unique records, so re-running the same payload never duplicates a composition. It writes each output through a unique private temporary file, `fsync`, and atomic rename. A failed replacement leaves the prior journal intact; a concurrent refresh re-reads the newly written journal while holding the lock.

`iteration_counter` remains monotonic. Set it to the larger of its stored value and the number of uniquely recorded experiments; it is display numbering, never an experiment identity.

Apply the four-state classification from proven wins/losses only:

| Status | Rule |
|--------|------|
| `inconclusive` | Fewer than 3 decisive proven results |
| `won` | At least 3 decisive proven results and hit rate ≥ 0.75 |
| `lost` | At least 3 decisive proven results and hit rate ≤ 0.25 |
| `mixed` | At least 3 decisive proven results and 0.25 < hit rate < 0.75 |

The minimum threshold of 3 decisive tests is load-bearing. Manual and unknown selections never lower it.

### Explicit bounded rebuild

Use a rebuild only when the journal is missing, corrupt, or older than version 4, or when the user explicitly asks to recover it. Reconcile from page 1 under the same five-page/eight-detail budget and run the helper with `--rebuild`. For an older valid journal it writes a private `.schema-<version>.backup` before atomically replacing the journal. A corrupt journal is never overwritten: ask the user to restore or move it aside first. If the producer reports more than five pages or more than eight eligible detailed results, label the rebuild partial and say exactly what it covered. Without a producer cursor, another page-1 rebuild cannot safely promise to progress into older history; do not claim a full replay merely because the local journal was replaced.

### JSON schema

```json
{
  "schema_version": 4,
  "site": {
    "key": "<site key — see derivation rule>",
    "name": "<from get-site-context>",
    "theme": "<from get-site-context, or null if not exposed>",
    "url": "<from get-site-context>"
  },
  "last_updated": "<ISO 8601 timestamp — wall-clock UTC at the moment of the run>",
  "iteration_counter": 0,
  "listing_coverage": {
    "complete": false,
    "pages_fetched": 5,
    "pages_total": 12,
    "result_correction_coverage": "partial",
    "reason": "The refresh covered the newest 500 completed experiments."
  },
  "experiments": {
    "42": {
      "experiment_id": 42,
      "listing_fingerprint": "<sha256>",
      "result_revision": "<producer revision or null>",
      "fingerprint": "<sha256>",
      "pattern_id": "headline_clarity",
      "outcome": "unknown_selection",
      "evidence": "unknown_selection",
      "lift_percent": null
    }
  },
  "stats": {
    "total_experiments_considered": 0,
    "concluded_with_winner": 0,
    "concluded_without_winner": 0,
    "patterns_with_signal": 0
  },
  "patterns": [
    {
      "pattern_id": "<from taxonomy>",
      "display_name": "<from taxonomy>",
      "status": "won|lost|mixed|inconclusive",
      "tests_total": 0,
      "tests_won": 0,
      "tests_lost": 0,
      "tests_inconclusive": 0,
      "hit_rate": null,
      "avg_lift_percent": null,
      "last_tested_at": null,
      "last_winning_block": null,
      "compositions_tried": [
        {
          "block_id": null,
          "experiment_id": null,
          "summary": "<short plain-English description of the structural recombination tested — e.g. 'hero + logo strip + single CTA'>",
          "outcome": "win|loss|inconclusive|manual_selection|unknown_selection",
          "evidence": "proven_result|manual_selection|unknown_selection",
          "ended_at": null
        }
      ],
      "notes": null
    }
  ]
}
```

Field notes:
- `iteration_counter` is the site's running experiment count, used by `accelerate-test` as the test number at the front of each experiment title (`"#<n> <Block>"`, where `n = iteration_counter + 1`) and as the x-axis index of the auto-research progress chart. It is global across rounds and blocks and only moves forward. See Step 5.
- `patterns_with_signal` counts distinct patterns with at least one decisive **proven** result. `total_experiments_considered` counts uniquely recorded entries, including `other`, manual selections, and unknown historical selections.
- `compositions_tried` has one entry per `experiment_id`. It preserves a structural recombination and its current best-known outcome. When the producer reports a corrected version of the same experiment, update that entry instead of appending a duplicate.
- `notes` is free-text carry-forward context for the next run: what has been learned about this pattern on this site that the stats alone don't capture (e.g. "outcome framing wins; social-proof framing has lost twice"). Update it, don't blank it.

### Markdown format

Regenerated from the JSON on every run. The user reads this; no skill parses it.

```markdown
# Learning journal -- [Site Name]

Last updated: [date]

Summary: [X] experiments analysed, [Y] with a clear winner, [Z] inconclusive.

## Patterns that win on your site

### [Display name]
- Won [N] of [M] tests ([hit_rate]%)
- Average improvement: +[lift]%
- Last tested: [date]
- Compositions tried: [short summaries of the structural recombinations and how each did]

## Patterns that haven't worked here

### [Display name]
- Won [N] of [M] tests ([hit_rate]%)
- Last tested: [date]
- [advisory note -- this is site-specific, not a universal rule]

## Mixed results

### [Display name]
- Won [N] of [M] tests
- Works sometimes, not a default

## Not enough data yet

### [Display name]
- [N] tests so far, need at least 3 decisive results before drawing conclusions
```

## Step 6 -- Print summary to user

Short, marketer-friendly. Follow the output style guide (`docs/output-style.md`). Example:

> **Learning journal updated** for [site name].
>
> 🔴 **New this week:** "Rewrite headline to match what visitors searched for" has now won 4 of 5 tests with an average +23% improvement. I'll lean on this when suggesting A/B tests.
>
> 🟡 **Still building evidence:** "Move the main button higher on the page" has 2 wins out of 3 -- one more test and I'll have a clearer picture.
>
> 🟢 **Not working here:** "Add urgency language to buttons" has lost all 3 tests. I'll stop leading with it unless you ask.
>
> *"Want me to suggest what to test next based on what we've learned?"*

**Hard rules for this output:**
- Never show `pattern_id` values. Always use `display_name`.
- Never say "journal file", "JSON", "schema", "parse", or "pattern taxonomy".
- Never recommend specific test ideas -- hand off to `accelerate-opportunities` or `accelerate-test`.
- If no patterns have enough data yet, say so plainly and encourage patience.
- State partial coverage and unknown/manual selections plainly. Never phrase them as statistical wins or losses.

## Pattern taxonomy

These are the 15 canonical suggestion patterns. The `pattern_id` is the machine key; the `display_name` is what the user sees.

| `pattern_id` | `display_name` |
|---|---|
| `headline_match_intent` | Rewrite headline to match what visitors searched for |
| `headline_clarity` | Rewrite headline for clarity |
| `cta_above_fold` | Move the main call-to-action higher on the page |
| `cta_copy` | Rewrite button or link text to be more specific |
| `social_proof` | Add social proof near the call-to-action |
| `testimonial` | Add a customer testimonial near the call-to-action |
| `urgency_copy` | Add urgency or scarcity language |
| `simplify_hero` | Simplify the hero section (remove clutter) |
| `pricing_display` | Change how pricing is shown (default period, anchoring) |
| `personalize_referrer` | Personalise content by traffic source |
| `personalize_geo` | Personalise content by visitor location |
| `personalize_device` | Personalise content by device type |
| `hero_image` | Change the hero image |
| `form_fields` | Change form field count or layout |
| `other` | Other / unclassified |

**This taxonomy is fixed.** Do not invent new pattern_ids during a run. If an experiment doesn't match a known pattern, it goes to `other`. The taxonomy grows only in toolkit releases.

## Rules

- **Never create, modify, or stop experiments.** This skill is read-only on WordPress.
- **Never recommend specific test ideas in the summary.** Hand off to other skills.
- **Never overwrite a corrupted journal.** Surface the error and let the user decide.
- **All per-site files are `chmod 600`.** Same security posture as credentials.
- **Old flat journals are abandoned, not migrated.** A site's first run under the new key starts a fresh journal in its `sites/<key>/` subdirectory.
- **Write atomically.** Temp file + rename. Never write directly to the target path.
- **Minimum 3 decisive tests before classification.** The `inconclusive` floor is non-negotiable.
